# Part 4: conservative migration and history reconciliation

The v3 migration is preview-first. `mintable migrate --source-file` or `--source-env` reads the legacy source without applying the v3 schema. It recognizes v1, v2 Plaid, v2 Teller fork, and mixed configurations. The preview lists retained accounts, integrations, columns, rule fields, backups, and warnings without credential values. Applying requires the preview hash, archives the original source and existing CSV outputs with private permissions where supported, and writes a separate v3 file using an atomic no-replace link. The legacy source and outputs remain usable.

The conversion retains reusable Google and CSV settings, templates, custom columns, rules, CSV import accounts, and Teller enrollments whose IDs and tokens can be recovered. It does not copy Plaid credentials into v3. Accounts without recoverable Teller enrollment metadata must reconnect. The v3 file starts pending, and `mintable fetch` refuses to export until activation.

Activation requires an explicit mapping for each old bank or CSV account to a new Teller/CSV account or archive-only status, a stable local account identity, a complete-month cutover, and distinct new output destinations. It verifies the source and CSV output backups still exist, previews account name changes and rule fields needing review, and removes legacy accounts mapped to archive. Google users manually duplicate the original spreadsheet, provide the archive ID, and confirm formulas and the empty new destination. Existing Sheets-only tokens cannot use Drive's whole-file copy endpoint. CSV users provide new paths that do not exist yet. The pending v3 file is backed up before atomic replacement. Migrated fetches cannot use the original destination or dates before cutover.

`mintable reconcile` is a separate offline CSV step for users who need continuous history. It requires full dates, provider transaction IDs, account mappings, and a reviewed complete cutover month for every active local account. It writes a new file with stable local account identities and provider-qualified transaction keys. It reports possible date/amount/description matches but never treats them as automatic duplicates. Missing IDs, old rows in the cutover month, and existing output files block apply. The input histories are never modified.

Rollback uses the original Mintable version, legacy config, and old output. No live bank, Google spreadsheet, or credential revocation is performed by migration. The Google OAuth and output rewrite corrections in Part 5 remain necessary for ongoing export correctness.

Verification: `npm test` covers legacy shapes, repeated apply, private backups, activation guards, and reconciliation. The Google archive copy itself is a manual action and cannot be verified by the offline migration tool.
